# pyOS — мини-ОС на Python (подобие Linux)

Учебный **симулятор операционной системы**, полностью написанный на Python.
Реализует виртуальную файловую систему, подсистему процессов с планировщиком,
пользователей с правами доступа, интерактивный шелл с пайпами и редиректами,
а также сетевые утилиты и пакетный менеджер. Ядро, ФС и процессы симулируются
внутри Python; сеть, снапшоты и очистка экрана при этом используют ресурсы хоста.

## Запуск

```bash
# из корня репозитория
python -m pyos
```

При загрузке появится приглашение входа. По умолчанию пароли у учётных записей
пустые, поэтому достаточно ввести имя и нажать Enter:

| Логин  | uid  | Домашний каталог |
|--------|------|------------------|
| root   | 0    | /root            |
| user   | 1000 | /home/user       |
| guest  | 1001 | /home/guest      |

> **Неинтерактивный запуск.** В окружении без TTY (например, фоновый процесс
> с закрытым stdin) `login()` при EOF автоматически входит как `root`, а REPL
> завершается на первом же EOF. Для прогонов без терминала подавайте команды
> через stdin: первая строка — логин (`root`), затем команды, последняя —
> `exit`.

> **PowerShell и smoke-прогоны.** PowerShell может показывать
> `NativeCommandError` на ожидаемом stderr pyos (например,
> `cat: Permission denied`) — это не traceback pyos. При перенаправлении
> вывода в файл кириллица может отображаться некорректно из-за кодировки
> консоли PowerShell. Для smoke-прогонов:
>
> ```powershell
> $env:PYTHONIOENCODING='utf-8'
> [Console]::OutputEncoding=[System.Text.Encoding]::UTF8
> ```
>
> Это заметка для оператора; поведение pyos она не меняет.

## Возможности

### Файловая система
- дерево узлов (файлы, каталоги, символические ссылки) в памяти;
- права доступа `rwx` для владельца/группы/остальных, как в POSIX
  (проверяется и право `x` на промежуточных каталогах);
- **жёсткие ссылки** (`ln` без `-s`): общий inode — данные, `uid/gid/mode`
  и счётчик `nlink`;
- рекурсивное копирование `cp -r`; копирование каталога в себя или своё
  поддерево отклоняется; `cp`/`cp -r` сохраняют `mode` источника;
- `rm -r` проверяет права вложенных каталогов и sticky-защиту до удаления
  (без частичного удаления);
- `glob` не раскрывает имена из каталогов без права `x`/`r`;
- `ls -l` и `stat` для явного symlink показывают саму ссылку (`lrwxrwxrwx`,
  `name -> target`), включая висячую; запись/`touch` через висячую ссылку
  создаёт её цель;
- `chmod` принимает восьмеричный режим `0..7777` и отклоняет невалидный;
- пути: абсолютные и относительные, `.`, `..`, `~`; `~user` не поддерживается
  (явная ошибка), завершающий `/` требует каталог;
- `/tmp` с правами `1777`, `/root` закрыт (`700`);
- inode, размеры, время модификации, `stat`;
- regular-файлы хранят **bytes**: `read_bytes()` возвращает точные байты,
  `read_file()` возвращает `str` только для валидного UTF-8 и иначе даёт
  `InvalidArgument`; размер файла (`stat`, `ls -l`) считается в байтах;
- `cp`, `cp -r`, `mv` и `ln` (жёсткая ссылка) переносят содержимое как bytes
  без перекодирования, поэтому бинарные файлы не искажаются.

> **Sticky bit.** `/tmp` создаётся с mode `1777`. Бит `0o1000` enforced для
> удаления и переименования записей: `rm`/`unlink`, `rmdir`, `rm -r` и
> `mv`/`rename` в sticky-каталоге разрешены только root, владельцу каталога
> или владельцу самой записи. Для hardlink проверяется владелец общего inode,
> для symlink — владелец ссылки (цель не трогается). `rm -r` сначала
> валидирует всё дерево: если защищена хотя бы одна вложенная запись, отказ
> целиком, без частичного удаления. `mv` защищает и от выноса чужого файла из
> sticky-каталога, и от перезаписи чужой цели. `cp` поверх существующего файла
> — не удаление directory entry: он по-прежнему регулируется правом `W` на
> файл. Отказ — `Permission denied` (errno 13).

### Устройства, /proc и dmesg
- `/dev/null` (`666`), `/dev/zero` (`666`), `/dev/random` (`666`),
  `/dev/full` (запись завершается с `No space left on device`);
- динамические файлы `/proc/meminfo`, `/proc/uptime`, `/proc/cpuinfo`,
  `/proc/version`, статусы `/proc/<pid>/status` и `/proc/self/status`;
  каталоги pid пересобираются по живой таблице процессов;
- `dmesg` — кольцевой буфер сообщений ядра (загрузка, сигналы и т.п.).

### Процессы и планировщик
- таблица процессов с PID, PPID, владельцем, состоянием (N/R/S/Z/T);
- планировщик с квантами и симулированным временем (тики), учитывающий
  **приоритет `nice`** (взвешенное распределение CPU — чем меньше `nice`,
  тем больше процесс получает времени);
- состояния `READY`/`RUNNING`/`BLOCKED`/`TERMINATED`;
- фоновые задания (`&`), `jobs`, `wait`, `waitpid`, `fg`, `bg`;
- `wait [pid|%N]` и `waitpid [pid|%N]` возвращают код задания: без аргументов
  ждут все активные задания и возвращают код последнего завершённого; `fg`
  дожидается выбранного задания и возвращает его код;
- `sleep` блокирует процесс на заданное число секунд; внутренне это
  `N × TICKS_PER_SECOND` тиков. Голый `sleep N &`
  использует отдельный блокирующий путь (без CPU-кванта), а фоновые
  pipeline/редиректы выполняются через общий путь как обычные задания;
- фоновые pipeline и редиректы исполняются целиком: `echo hello | cat &`
  печатает `hello`, `sleep 1 > /tmp/f &` создаёт `/tmp/f`;
- `kill [-signal] pid ...` отправляет сигнал процессу. Поддерживаются числовые
  сигналы и имена из `pyos/signals.py`, например `-TERM`, `-SIGTERM`, `-KILL`,
  `-SIGKILL`, `-9`, `-15`. По умолчанию используется `SIGTERM`; сигналы с
  завершающим действием завершают процесс и устанавливают код выхода
  `128 + signal`. Сигналы с действием `ign` (`SIGCHLD`, `SIGWINCH` и т.п. по
  `DEFAULT_ACTION`) доставляются, но процесс не завершают; `kill` возвращает
  `0`. `kill -l` печатает список поддерживаемых сигналов в формате
  `<номер> <имя> SIG<имя>`; `kill -l TERM` и `kill -l 9` показывают
  номер/имя одного сигнала.

### Шелл и переменные
- конвейеры `|`, редиректы `>`, `>>`, `<`;
- фоновые задания `&` и разделитель `;`;
- логические операторы `&&` и `||` (`a && b` — `b` при успехе `a`,
  `a || b` — `b` при ошибке `a`); пустая команда после `&&`/`||` —
  синтаксическая ошибка, но только если до неё дошла очередь
  (`echo hi &&` — ошибка, `echo hi ||` — нет, срабатывает short-circuit);
- кавычки, экранирование (в одинарных кавычках и после `\` переменные
  не раскрываются);
- раскрытие `$VAR` / `${VAR}` и bash-операторы: `${VAR:-word}` (значение по
  умолчанию), `${VAR:=word}` (присвоить по умолчанию), `${VAR:+word}`
  (альтернатива), `${VAR:?word}` (ошибка, если переменная не задана или пуста);
- переменные раскрываются заново перед каждым top-level сегментом строки
  (`;`, `&&`, `||`), поэтому `NAME=X; echo $NAME` и
  `NAME=X; echo ${NAME:-guest}` печатают `X`, а `A=1; B=2; echo $A$B` — `12`;
  внутри одного конвейера раскрытие остаётся однократным;
- `${VAR:=word}` сохраняет присвоенное значение в шелле, а не только в
  подставленном тексте; `cd /tmp; echo $PWD` печатает новый каталог, потому
  что `PWD` пересчитывается перед каждым сегментом;
- специальные переменные `$?` (код возврата) и `$$` (PID, под которым
  выступает оболочка; в текущей реализации это PID `init`, то есть 1);
  код фонового задания попадает в `$?` только после явного `wait`/`fg`,
  а не асинхронно из worker'а;
- **локальные переменные** `VAR=value`, `export`, `unset`, `set`
  (префикс `VAR=value команда` передаёт переменную только команде);
- подстановка шаблонов `*`, `?`, `[...]` в незакавыченных аргументах;
- история, алиасы `alias`/`unalias`;
- `su` и `sudo` (смена пользователя, запуск от root);
- `nice [-n N] команда` или `nice N команда` — запуск с приоритетом `N`;
  поддерживаются формы `-n N`, `-nN`, голое `N`, голое `-N`; диапазон `N` —
  от `-20` до `19`; если указан только `nice команда`, приоритет
  увеличивается на `10`. Некорректное или внедиапазонное значение `N`
  приводит к ошибке `InvalidArgument`;
- голый `nice` без аргументов печатает текущий nice оболочки (в текущей
  реализации `0`); `nice -n 5` без команды завершается ошибкой
  `nice: missing command operand`;
- `ulimit -f [блоки]` — лимит размера файла (в 1K-блоках), применяется
  при записи через редиректы; `unlimited` снимает лимит.

### Сеть
- `curl` и `wget` выполняют **реальные** HTTP/HTTPS-запросы через
  `urllib.request` (используется сеть хоста, поэтому нужен доступ в интернет);
- `curl -v` — вывод заголовков, `-o файл` — сохранить в виртуальную ФС,
  `-L` — следовать редиректам (по умолчанию не следует);
- `wget [-O файл] [-q]` — скачивание в виртуальную ФС, редиректам следует
  по умолчанию; имя файла берётся из URL;
- `curl -o FILE` и `wget -O FILE` сохраняют **точные bytes** ответа:
  тело не декодируется и не проходит через `errors="replace"`;
- `curl` без `-o` печатает тело как текст только для валидного UTF-8.
  Binary stdout подавляется с ошибкой
  `curl: binary output suppressed; use -o FILE` и ненулевым кодом;
- `wget` всегда пишет файл (`-O` или имя из URL) и не имеет пути вывода тела
  в stdout, поэтому для него binary-safe означает точную запись bytes в файл;
- `curl -v -o FILE` печатает заголовки в stdout, а в файл пишет только тело;
  без `-o` заголовки и тело выводятся вместе;
- кодировка текстового ответа берётся из `Content-Type` или определяется по
  содержимому.

### Текстовые утилиты и binary-файлы

После перехода ФС на bytes у текстовых команд явная политика:

- `wc -c` считает точные байты через `read_bytes()`/`len(bytes)` и работает
  на binary-файлах без ошибки. Режимы `-l`/`-w` и режим по умолчанию требуют
  текста;
- `cat` печатает валидный UTF-8 как раньше, а для binary даёт понятную ошибку
  `cat: binary file: PATH (not valid UTF-8)` без traceback и без raw-вывода;
- `grep` не печатает строки binary-файла. Если шаблон найден по точным bytes,
  выводится `Binary file PATH matches`;
- `head`, `tail`, `sort`, `uniq`, `rev` и `cut` на невалидном UTF-8 дают
  ошибку `<команда>: not valid UTF-8 text: PATH` и не обрабатывают файл
  частично;
- `tr` по-прежнему читает только stdin. Валидный UTF-8 обрабатывается как
  раньше, невалидный stdin даёт `tr: not valid UTF-8 text: <stdin>`;
  файловые операнды для `tr` не поддерживаются.

Бинарный pipeline не поддерживается: потоки шелла (`|`, stdin/stdout команд)
остаются текстовыми. Это отдельный долг, запланированный на BS-7.

### Пакетный менеджер

`pkg` — основной путь установки пакетов в pyOS. `makepkg` и `PKGBUILD` остаются
для совместимости и локальной сборки, но для репозиториев используется
`.pkg.json` + `pkg install`.

Пакет — это JSON-файл (текстовый контейнер); файлы внутри него могут быть
текстовыми или бинарными (base64). Код из пакета не выполняется: pyOS только
проверяет JSON, зависимости, пути, владельцев, sha256 и размер, после чего
записывает файлы в виртуальную ФС.

#### Формат `.pkg.json`

```json
{
  "format": 1,
  "name": "hello",
  "version": "1.0",
  "release": 1,
  "arch": "any",
  "description": "A friendly greeting",
  "depends": ["base>=1.0"],
  "provides": ["hello"],
  "conflicts": ["hello-old"],
  "files": [
    {
      "path": "/usr/bin/hello",
      "mode": "0755",
      "owner": "root",
      "group": "root",
      "encoding": "utf-8",
      "content": "#!/bin/sh\necho Hello\n"
    }
  ]
}
```

Обязательные поля: `format`, `name`, `version`, `files`. `release` по
умолчанию `1`, `arch` — `any`. Для файлов поддерживаются `encoding`:

- `"utf-8"` / `"utf8"` (значение по умолчанию, если поле отсутствует) —
  `content` содержит текст;
- `"base64"` — `content` содержит ASCII-строку с base64-представлением
  точных bytes.

Невалидный base64 и неизвестный `encoding` отклоняются с `InvalidArgument`.
Старые пакеты без поля `encoding` продолжают устанавливаться как UTF-8.
`tar`/`zip`-архивы, scriptlets и hooks не поддерживаются. `signature` может
присутствовать в индексе, но не проверяется.

#### Сборка через `pkg pack`

`pkg pack` — предпочтительный простой способ собрать `.pkg.json` из каталога
виртуальной ФС. Он не читает `PKGBUILD`, не выполняет `build()`/`package()` и
не запускает код из каталога.

```text
mkdir -p /tmp/hello-root/usr/bin
echo 'echo hello' > /tmp/hello-root/usr/bin/hello
chmod 755 /tmp/hello-root/usr/bin/hello

pkg pack /tmp/hello-root /var/cache/packages/hello-1.0.0-1-any.pkg.json \
  --name hello --version 1.0.0 --release 1 --arch any \
  --depends libc --description "Hello utility"

pkg install /var/cache/packages/hello-1.0.0-1-any.pkg.json
```

Для каждого regular-файла `pkg pack` читает точные bytes: содержимое,
являющееся валидным UTF-8, сохраняется с `encoding: "utf-8"`, остальное
автоматически кодируется в `encoding: "base64"`.

Каталоги в `files[]` не перечисляются: `pkg install` создаёт их неявно.
`mode`, `owner` и `group` берутся из виртуальной ФС. `--depends` можно повторять;
`--release` по умолчанию `1`, `--arch` — `any`. `--dry-run` печатает файлы,
которые попадут в пакет, но не создаёт выходной файл. `pkg pack` работает
только от root.

#### Команды

```text
pkg install <name> [--dry-run]
pkg install <name>@<repo> [--dry-run]
pkg install <name>=<version> [--dry-run]     # также >=, <=, >, <
pkg install <path/to/file.pkg.json> [--dry-run]

pkg pack <root-dir> <output-pkg> --name <name> --version <version> \
  [--release <n>] [--arch <arch>] [--depends <dep>]... \
  [--description <text>] [--license <text>] [--dry-run]

pkg upgrade [<name>...] [--dry-run] [--force]
pkg remove <name> [--force] [--dry-run]
pkg list
pkg info <name>
pkg search <query>

pkg repo add <name> <url> [--type http|path] [--priority N]
pkg repo remove <name>
pkg repo list
pkg repo update [<name>...]
pkg repo enable <name>
pkg repo disable <name>
```

`pkg install <name>` ищет пакет в кэше включённых репозиториев, рекурсивно
разрешает зависимости и устанавливает их в порядке от зависимостей к
зависимому пакету. `@repo` ограничивает только корневой пакет; его зависимости
могут быть взяты из других включённых репозиториев.

`pkg upgrade` обновляет только на более новые версии. `--dry-run` печатает
план, `held back` и предупреждения, ничего не записывая. `--force` разрешает
обновление, ломающее обратную зависимость, но выводит предупреждение; файловые
конфликты `--force` не обходит.

`pkg remove` отказывается удалять пакет, от которого зависят другие пакеты.
`--force` снимает эту проверку.

#### Права доступа

| Команда | Кто может выполнять |
|---|---|
| `pkg install`, `pkg upgrade`, `pkg remove`, `pkg pack` | root |
| `pkg list`, `pkg info` | все пользователи |
| `pkg repo add`, `remove`, `update`, `enable`, `disable` | root |
| `pkg search` | все пользователи |
| `pkg repo list` | все пользователи |
| `pkg help` / `pkg` без аргументов | все пользователи |
| `makepkg` | root |

Read-only команды (`pkg search`, `pkg list`, `pkg info`, `pkg repo list`)
не требуют root. `pkg search` и `pkg repo list` читают только кэш индексов;
`pkg list` — installed DB; `pkg info` — installed DB, legacy-кэш пакетов и
кэши индексов репозиториев (без сети и без автообновления).

#### Установка по имени и кэш

Перед `pkg install <name>` нужен кэш индекса. Если его нет:

```text
repo: no cached index for 'core', run pkg repo update first
```

`pkg install` не запускает `pkg repo update` автоматически. Скачанный индекс
лежит в `/var/cache/repos/<repo>/index.json`, метаданные — в
`/var/cache/repos/<repo>/index.meta.json`. Скачанный пакет лежит в
`/var/cache/packages/<repo>/<filename>`.

При установке проверяются:

- `sha256` индекса пакета и фактических bytes скачанного файла пакета:
  package payload кэшируется и хешируется как bytes, без перекодирования
  текста;
- заявленный `size` (превышение — ошибка), тоже в байтах;
- зависимости и их version-spec;
- файловые конфликты с текущими владельцами;
- запрет downgrade;
- абсолютность и отсутствие `..` в путях.

Повторная установка уже установленной версии отклоняется. Для обновления
используйте `pkg upgrade`; для установки другой версии — явный version-spec,
если это не downgrade.

### Репозитории пакетов

Репозиторий — это каталог с `index.json` и пакетами. Поддерживаются два типа:

- `http` — только `https://`, URL обязан заканчиваться `/`;
- `path` — абсолютный путь внутри виртуальной ФС, тоже с `/` на конце.

`http://` запрещён. Автоматического обновления индекса нет: `pkg repo update`
нужно вызывать явно.

#### Формат `repos.json`

Файл: `/etc/pyos/repos.json`.

```json
{
  "format": 1,
  "repos": [
    {
      "name": "core",
      "url": "https://raw.githubusercontent.com/OWNER/pyos-packages/main/",
      "type": "http",
      "enabled": true,
      "priority": 10
    },
    {
      "name": "local",
      "url": "/srv/local/",
      "type": "path",
      "enabled": false,
      "priority": 100
    }
  ]
}
```

`priority` сравнивается как целое: большее значение важнее. При одинаковом
priority и одинаковом имени пакета установка не выбирает репозиторий наугад, а
завершается ошибкой `ambiguous package`. `enabled: false` исключает репозиторий
из `update`, `search`, `install` и `upgrade`; `pkg repo list` показывает
состояние, а в колонке `TYPE` — фактический транспорт: `https` для `https://`
URL (даже если в конфиге поле `type` исторически равно `"http"`) и `path` для
`path`-репозиториев.

#### Формат `index.json`

```json
{
  "format": 1,
  "repo": "core",
  "generated": "2026-10-23T22:40:00Z",
  "packages": [
    {
      "name": "hello",
      "version": "1.0",
      "release": 1,
      "arch": "any",
      "filename": "hello-1.0.pkg.json",
      "url": "packages/hello-1.0.pkg.json",
      "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "size": 512,
      "description": "A friendly greeting",
      "license": "MIT",
      "depends": ["base>=1.0"],
      "provides": ["hello"],
      "conflicts": ["hello-old"],
      "signature": null
    }
  ]
}
```

`url` и `filename` обязаны быть относительными; абсолютные URL, `..` и выход за
базовый URL репозитория запрещены. `sha256` обязателен. `repo` в индексе должен
совпадать с именем репозитория в `repos.json`; несовпадение даёт warning при
`update`, но индекс всё равно кэшируется.

#### Полный workflow

1. Собрать `.pkg.json` через `pkg pack` (предпочтительно), создать вручную
   или собрать пакет через legacy `makepkg`.
2. Положить файл в `pyos-packages/packages/`.
3. Сгенерировать `index.json` через `tools/gen_repo_index.py`.
4. Залить `index.json` и `packages/` в GitHub.
5. В pyOS:

   ```text
   pkg repo add core https://raw.githubusercontent.com/OWNER/pyos-packages/main/
   pkg repo update
   pkg search hello
   pkg install hello
   pkg upgrade --dry-run
   pkg upgrade
   pkg list
   pkg info hello
   pkg remove hello
   ```

6. Для локальной проверки без сети использовать `type=path`:

   ```text
   pkg repo add local /srv/local/ --type path
   pkg repo update
   pkg install hello
   ```

#### save/load и оффлайн-кэш

`save` сериализует виртуальную ФС, кроме `/dev` и `/proc`. Поэтому в снапшот
попадают:

- `/var/cache/repos/<repo>/index.json` и `index.meta.json`;
- `/var/cache/packages/<repo>/<filename>`;
- `/var/lib/packages/installed/<name>.json`;
- `/var/lib/packages/file-owners.json`.

После `load` можно устанавливать пакеты из уже скачанного кэша без обращения к
источнику. Для получения нового индекса или пакета, которых нет в кэше, всё
равно нужен `pkg repo update` и доступ к репозиторию.

#### Ограничения

- `pkg pack` включает только regular-файлы, но поддерживает и текст UTF-8,
  и бинарные данные: `encoding` выбирается автоматически (`utf-8` или
  `base64`). Симлинки, hardlinks, special files, tar/zip-архивы,
  scriptlets/hooks не поддерживаются. `makepkg` остаётся legacy-путём.
- Старые пакеты без `encoding` трактуются как UTF-8 и продолжают
  устанавливаться; base64-пакеты требуют явного `encoding: "base64"`.
- `provides` парсится, но не используется для разрешения зависимостей.
  `conflicts` проверяется только по точным именам установленных пакетов, без
  виртуальных provides и version-spec.
- Подписи не проверяются; `signature` — заглушка.
- `http://` запрещён; `--allow-http` отсутствует.
- Нет автоматического `pkg repo update`, ETag/Last-Modified и TTL индекса.
- Нет транзакционного rollback/journal при частичном сбое применения.
- Нет downgrade: ни через `pkg upgrade`, ни через `pkg install` более старой
  версии.
- Файловые конфликты не обходятся `--force`.
- `sha256` обязателен для пакетов из индекса; локальный
  `pkg install <path.pkg.json>` работает без sha256, потому что файл не
  скачивается.
- `pkg repo update` обновляет только включённые репозитории, если имена не
  указаны явно. Явное обновление disabled-репозитория даёт ошибку с подсказкой
  `pkg repo enable`.
- Ошибка в одном репозитории при `pkg repo update` превращается в warning; другие
  репозитории продолжают обновляться.

### Состояние и лимиты
- `save <файл>` — сохраняет ФС и пользователей в JSON **на реальном хосте**
  (аргумент — путь к файлу операционной системы, не виртуальной ФС);
- `load <файл>` — полностью заменяет текущее состояние ФС, пользователей
  и `hostname` из снапшота (только root);
- текущий формат снапшота — **version 3**. `load` принимает также версии
  `1` и `2`, поэтому старые снапшоты совместимы;
- в version 3 валидный UTF-8 хранится читаемым текстом в поле `data`;
  binary-содержимое сохраняется с `encoding: "base64"` и base64-строкой
  в `data`;
- `/proc` и `/dev` не сериализуются и после `load` пересоздаются ядром как
  виртуальные узлы;
- hardlinks, номера inode и времена файлов по-прежнему не восстанавливаются
  (DOCUMENTED LIMIT): после `load` жёсткие ссылки становятся независимыми
  файлами, хотя `uid/gid/mode` сохраняются;
- `ulimit -f` — см. раздел «Шелл и переменные».

## Ограничения

- Это **симулятор**: процессы — объекты с тиками, а не реальные потоки ОС.
- Файловая система хранится только в памяти и теряется при выходе, если не
  сохранить её командой `save`.
- `save`/`load` работают с JSON-файлами на реальном хосте (не в виртуальной
  ФС); `load` полностью заменяет текущее состояние.
- Снапшот не сохраняет жёсткие ссылки, номера inode и времена файлов;
  после `load` жёсткие ссылки становятся независимыми файлами, но их
  `uid/gid/mode` сохраняются.
- `/proc` и `/dev` не сериализуются: после `load` они пересоздаются ядром
  как виртуальные узлы. Старые снапшоты, где они лежат обычными файлами,
  в этой части игнорируются.
- `glob` возвращает абсолютные пути, а шаблон `*/` не отсекает файлы: это
  известный долг, фикс требует изменения API glob или шелла.
- Sticky-бит (`0o1000`) enforced для удаления/переименования записей, но
  display и смежные биты остаются упрощёнными: `perm_string()` (`ls -l`,
  `stat`) не показывает `t`/`T`, sticky виден только числом в `mode`;
  `ls -d` не реализован; `setuid`/`setgid` не enforced (см. ниже);
  `rm -r` не проверяет `W|X` у пустых подкаталогов (`if node.children` в
  `_check_rmtree`) — известный дефект, не связанный со sticky.
- `SIGSTOP`, `SIGTSTP` и `SIGCONT` не поддерживаются (в том числе в числовой
  форме `-18`, `-19`, `-20`): pyOS не реализует остановку и продолжение
  процессов, `kill` отклоняет их с ошибкой. Полной POSIX-семантики сигналов
  нет: завершающий сигнал не доставляется обработчику, а сразу завершает
  процесс; сигналы с действием `ign` процесс не завершают.
- Ядрового zombie/waitpid нет: `ProcessState.ZOMBIE` объявлен, но нигде не
  присваивается, завершённые процессы сразу удаляются из `kernel.processes`.
  Статус фонового задания шелл читает из сохранённой ссылки `job["proc"]`
  (`exit_code`), а не через reaping родителем.
- `wait`/`waitpid` работают только с заданиями текущего шелла (`%N` или PID);
  реального parent-child waitpid и wait для произвольных процессов нет.
- `fg` дожидается завершения задания и возвращает его код; `bg` лишь печатает
  задание и не возобновляет его. Полноценного job control нет.
- Завершённые задания остаются в истории `jobs` до выхода из шелла: `jobs`
  продолжает показывать `Done(<код>)`, а `wait <pid>` по завершённому заданию
  возвращает сохранённый `exit_code`. Номера заданий (`%N`) не
  переиспользуются. Это упрощение симулятора, а не POSIX-точная модель job
  control; автоматической очистки списка заданий нет.
- `kernel.create_process()` не проверяет диапазон `nice` (это делает только
  встроенный `nice`); `Scheduler.block()` не удаляет процесс из `ready`;
  `drain()`/`run_until()` молча останавливаются на лимите тиков. Это
  внутренние ограничения симулятора, а не гарантии POSIX.
- Фоновые задания выполняются отложенно: `worker` завершает команду в момент
  выхода процесса и вручную двигает `scheduler.clock`. Связка хрупкая —
  менять её нужно вместе с тестами планировщика.
- Дальнейшее развитие планировщика (stage 3) отложено. Текущая модель —
  симуляция тиков и `nice`; вытесняющей многозадачности и реального
  parent-child waitpid нет.
- Бинарный pipeline не поддерживается: stdin/stdout команд и пайпы `|`
  остаются текстовыми. Бинарные данные можно сохранять через сетевые
  `-o`/`-O` и читать через `read_bytes()`, но не прогонять через конвейер.
  Это долг BS-7.
- `setuid`/`setgid`-биты отображаются в `mode`, но не enforced: смена
  эффективных uid/gid при исполнении файла не моделируется.
- `ulimit -f` ограничивает только запись через редиректы `>`/`>>`;
  `cp`, `wget`, `pkg` и `save` этот лимит не соблюдают.
- `sudo` не запрашивает пароль и не проверяет sudoers — любой пользователь
  может запустить команду от root.
- `pkg install` и `pkg info` выбирают версию из кэша через `pkgvercmp`:
  `1.10` новее `1.9`, поддерживаются `epoch`, `version` и `release`;
  сравнение упрощённое — числовые и буквенные сегменты, без полной
  семантики alpm.
- `.pkg.json` поддерживает `encoding: "utf-8"`/`"utf8"` и `"base64"`;
  старые пакеты без `encoding` совместимы. Зависимости проверяются по имени
  и version-spec, но `provides` не используется. `conflicts` проверяется
  только по точным именам установленных пакетов, без version-spec;
  `pkg remove --force` может оставить сломанные зависимости.
- `pkg upgrade` не делает даунгрейдов; обратные зависимости проверяются, но
  `--force` может их сломать; файловые конфликты и sha256 им не обходятся.
  `pkg repo update` нужно запускать явно.
- `pkg repo update` для `type: "http"` использует реальную сеть хоста:
  `http://` запрещён, допускается только `https://`; редиректы и таймаут
  10 секунд, без retry и TTL, индекс ограничен 4 MiB.
- `clear` очищает реальный терминал хоста, а не виртуальный экран.
- Пароли хранятся как SHA-256 без «соли»; это учебный код, не для продакшена.
- `df`/`free` показывают условные значения.
